# Managing Degree Pages on the New Website

Executive summary · Draft · November 2026

## The short version

Degree pages are moving into the block editor, but that isn't the real change. The real change is that a degree page stops being a form we fill out and becomes a page we own. Today, every degree has the same layout, fixed in code. We customize it through about 35 fields spread across twelve tabs, and when the layout doesn't suit a program, the only workaround is to build the page by hand. On the new site, every degree starts from a standard layout. From then on, we can rearrange it, remove sections and add new ones, just as we would on any other page.

The data stays automatic. Descriptions, tuition, deadlines, admission requirements, career outcomes, employment projections, careers, highlights and testimonials all come from the Search Service, the program data system the current site already imports from, and they update on the page by themselves. **We arrange the page, and the Search Service keeps the facts current.**

## How a new degree arrives

When a program is added to the Search Service, the next import creates its degree page with the standard layout already in place. That page is complete before anyone touches it. It has the program overview, description, deadlines and requirements, outcomes and projections, careers, and the shared sections that appear on every degree. Later imports update the program information but never change the layout or anything we have written.

That means work on a new degree is optional. A new program has a correct page from its first day, and we spend our time on the degrees where better content makes a real difference.

## What we edit, and what updates itself

- **Search Service information updates itself.** The Search Service takes in new program data once a month, and our pages pick up the changes within hours of each import. When one of these facts is wrong, we fix it in the Search Service, not on the page, and the correction then fixes every page that shows it. The catch is timing. A fix that comes in through the monthly import can take up to a month to appear. We haven't yet confirmed whether a correction can be made directly in the Search Service to get it on the page sooner.
- **The layout is ours.** We can move sections around. For example, a graduate program with an early deadline can put deadlines above the description. We can also remove a section that doesn't serve a program, or add one that's missing.
- **Editorial sections are ours.** Course overview, skills, admission copy, curated testimonials and news are added from a short set of ready-made degree sections in the editor, then written for each degree.
- **Shared sections are edited once.** Badges, Start Your Application, the UCF Online callout and the message shown when a program has no deadlines posted each live in one place. An edit there changes every degree at once. If one degree needs something different, we detach that section on that page and edit it there.

That puts our effort where it belongs: on the story each program tells, not on re-entering data that already exists somewhere else.

## When the Search Service text isn't right for a page

Sometimes the catalog description is accurate but isn't what we want a prospective student to read first. In those cases, the description, highlights, testimonials, careers and admission requirements can each be converted into regular editable text: a copy of the current wording that we then own. The tradeoff is real. **Once we convert a section, it stops updating**, so a later catalog change won't reach that page.

Tuition, deadlines, outcomes and projections can't be converted, on purpose. An out-of-date deadline looks exactly like a current one, and no improvement in wording is worth a student missing an application date because our page went stale. If those numbers are wrong, the fix belongs in the Search Service.

Conversion should be the exception, not a habit. We should keep a short list of the degrees where we've used it, so we know which pages to check when the catalog changes.

## When the standard layout changes

Every degree gets its own copy of the standard layout, so a change to the standard layout later only affects degrees created after it. That is the price of being able to customize every page, and we think it's the right trade. Degrees nobody has edited can be updated to the new layout automatically. Degrees we've customized are listed for us to update by hand, so nothing we've written is overwritten unless we choose that.

The standard layout is therefore the most important decision we make before launch. It is the starting point for every degree, and getting it right up front saves hand edits later.

## What goes away

The twelve-tab field form on every degree goes away. That includes Program at a Glance, Deadlines, Start Your Application, Course Overview, Quotes, Skills, Admission Requirements, UCF Online, News and the rest. Their jobs are now done by sections on the page itself, edited where we can see them. The few per-degree settings that remain move into the editor's sidebar: the undergraduate Slate ID for Request Information, and the controls that tell the import to leave a degree alone.

The new site also starts fresh. We are not moving the current degree pages over. If we bring curated content across later, that will be a separate project, and it will follow the approach described here.

## What we still need to decide

- **How we correct Search Service data.** Since fixes belong in the Search Service, we need a named process for requesting corrections. We also need a plan for the ones that can't wait for the next monthly import, such as a wrong application deadline in the middle of an admissions cycle.
- **The standard layout.** We need to decide which sections it includes, in what order, and whether details like program length stay.
- **Which sections every degree must keep.** We can lock a section so it can be moved but not deleted. Our plan is to start with no locks and add them only if we find we need them.

These are content decisions, not technical ones. They're ours to make, and we should make them before the standard layout is final.
